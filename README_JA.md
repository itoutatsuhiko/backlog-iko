# Backlog 課題移行ツール v1.0.0

別スペースのBacklogへ課題をコピーする、Python標準ライブラリのみのコマンドラインツールです。Webサーバーやデータベース、pipパッケージのインストールは不要です。

**公式の移行ツールとは別の独自実装です。実際のBacklogアカウントでの実行確認はしていません。まず少数件で試し、画面でも照合してください。**

想定する今回の状況は、課題約400件、Git不要、プロジェクト設定をインポート済み、移行元・先に状態が9〜12個あるケースです。状態の追加APIは一切呼びません。状態名の変更履歴も再実行せず、課題を作成したあと、既存の移行先の状態IDに更新します。

## 1. 対象と制限を先に確認

| 項目 | このツールの動作 |
|---|---|
| 件名・詳細 | コピー。詳細末尾に旧課題キー・旧URL・元の作成者／更新者・日時・識別マーカーを追記 |
| 種別・優先度・現在の状態・完了理由 | 既存の移行先IDへ対応付け。状態や設定項目を新規作成しない |
| 担当者 | NulabアカウントID、次にメールアドレスが一意一致する場合に自動対応。表示名だけでは決めない |
| 開始日・期限日・予定時間・実績時間 | コピー。ゼロの値も保持 |
| カテゴリー・バージョン・マイルストーン | 既存設定に対応付け。同じ名称が一意なら自動対応 |
| 親子課題 | 親を先に作成し、新しい課題IDへ対応付け |
| コメント | 本文に元の投稿者・作成日時・更新日時を記載してコピー |
| 旧変更履歴 | 取得できるコメントの `changeLog` を、参照用JSONテキストとしてコメントへ記録。ネイティブな変更履歴としての再現ではない |
| 添付ファイル | 取得可能な現在の課題添付一覧をコピー。**1ファイルにつき新しい「移行添付ファイル」コメントに添付** |
| カスタム属性 | 定義が移行先にあり、型と選択肢が対応する文字列・文章・数値・日付・単一リスト・複数リスト・チェックボックス・ラジオに対応 |
| 課題番号・ID | 新しく採番される。旧→新の対応表を `issue_mapping.csv` に保存 |
| 登録者・登録日時 | システム上はAPI実行者・移行時点になる。元の値は詳細／コメント本文に記録 |

### 対象外・完全には再現できないもの

- **Wiki、ドキュメント、プロジェクト共有ファイル、Git、ユーザー登録、プロジェクト設定、Webhook・外部連携は移行しません。** 課題にリンクされた共有ファイルも対象外です。
- 添付ファイルと「元のコメント」の所属関係は再現しません。元のコメントはテキストでコピーし、ファイルは別の移行用コメントに添付します。
- 本文の旧課題リンク・旧添付URL・画像埋め込み・Wikiリンクなどは新URLへ自動書き換えしません。コピーしたファイルは新しい添付から取得できますが、元の本文中の画像やリンクは引き続き旧スペースを参照することがあります。
- 関連課題（親子以外）、スター、既読、ウォッチ、通知履歴、削除済み課題・削除済み添付・取得不能な過去版は対象外です。
- カスタム属性のリストの「その他入力」、未知の属性型・値形式は、推測で変換せず停止します。欠落を黙って無視して続行する機能はありません。
- 本ツールは一回限りのスナップショットコピー用です。継続同期・差分同期・移行済みデータへの自動上書き・自動ロールバックには対応しません。
- APIの権限・プラン・容量・入力文字数制限などは実環境に依存します。`check` が成功しても、登録APIの全制約を事前に保証するものではありません。

移行元は、照合・リンク確認・対象外データの別途対応がすべて終わるまで削除・解約しないでください。

## 2. 必要な準備

Python 3.10以上のMacまたはLinux環境が必要です。確認コマンド:

```bash
python3 --version
```

Windowsネイティブは対象外です（プロセスの排他制御に `fcntl` を使用）。開発・テストはPython 3.13.5のLinuxコンテナで実施しました。実機のmacOS・Backlog本番環境では未検証です。

移行元の全対象課題・コメント・添付を閲覧できるAPIキーと、移行先プロジェクトで課題の追加・更新・コメント・添付操作が可能なAPIキーを準備してください。権限はキーを発行したユーザーの権限に従います。

移行先は、**設定はあるが課題がないプロジェクト**を推奨します。設定インポート済みでも構いません。以前の公式ツールの失敗で課題が一部残っている場合、本ツールはそれを照合・統合しません。まず別の空のテストプロジェクトで確認してください。スクリプトが勝手に既存課題を削除することはありません。

移行先に必要な状態・種別・カテゴリー・バージョン・カスタム属性を用意してください。担当者として引き継ぐユーザーは移行先プロジェクトに参加させます。**過去にコメントしただけのユーザーを、このスクリプトのために全員登録する必要はありません。** 元の名前は本文に記録します。

準備開始から最終確認が終わるまで、元・先プロジェクトへの他の書き込みを停止します。通知メール・Slack・Webhook等が発火する可能性があるため、関係者へ事前連絡し、必要な連携の停止を管理者と調整してください。本ツールは設定変更や通知の全抑止は行いません。

## 3. 設定する

ZIPを展開し、ターミナルでフォルダへ移動します。以下のパスは展開先に合わせて変更してください。

```bash
cd ~/Downloads/backlog_api_migrator
cp config.example.json config.json
```

`config.json` をエディタで開き、主に以下の4点を変更します。

```json
{
  "source": {
    "url": "https://old-company.backlog.jp",
    "project_key": "OLDPJ",
    "api_key_env": "BACKLOG_SRC_API_KEY"
  },
  "destination": {
    "url": "https://new-company.backlog.jp",
    "project_key": "NEWPJ",
    "api_key_env": "BACKLOG_DST_API_KEY"
  },
  "work_dir": "work"
}
```

サンプルにある `options` は、最初はそのままにしてください。省略時もサンプルと同じ既定値になります。URLには `/view/...` や `/projects/...` を付けずスペースのルートURLを指定します。`backlog.jp` / `backlog.com` / `backlogtool.com` のHTTPSだけを許可します。

続いて、同じターミナルでAPIキーを入力します。

```bash
source ./api_keys.sh
```

元・先それぞれのキーを順番に入力し、Enterを押します。入力内容は画面に表示されず、シェルのコマンド履歴や設定ファイルにもキーを書きません。キーはそのターミナルの環境変数に設定します。ターミナルを閉じたら再入力が必要です。

環境変数は子プロセスから参照できます。共有端末や第三者のプロセスがある環境での実行は避け、`set -x` 等のシェルトレースを無効にして作業してください。APIキーをチャットへ貼り付けないでください。

## 4. スナップショット取得と対応表生成（書き込みなし）

```bash
python3 backlog_migrate.py prepare
```

このコマンドは、元・先の設定を読み取り、元の全課題・コメント・添付をローカルへ保存します。**移行先への登録はまだ行いません。** 途中で失敗した `prepare` は同じコマンドで再実行できます。準備が完了して `snapshot.json` ができた後は、誤上書きを防ぐため再度の `prepare` を拒否します。

生成物の例:

```text
work/
  snapshot.json                 全課題の取得時点データ
  source_catalog.json           元の設定一覧
  destination_catalog.json      先の設定一覧（check時にも更新）
  mapping.json                  ID対応表【手動調整するファイル】
  mapping_report.md             対応表の読みやすい表示（参照用）
  source/                       課題ごとの元データJSON
  files/                        添付の実体（ID単位。元の名前はJSONで管理）
```

これらには個人情報や社内情報、添付ファイルが含まれます。既定でアクセス権を制限しますが、暗号化はしていません。公開Webディレクトリや共有Git、公開クラウドフォルダへ置かないでください。

## 5. 対応表を確認する

`work/mapping_report.md` と `work/destination_catalog.json` を参考に、`work/mapping.json` を確認します。

以下は一部分だけの例です。実際には生成されたファイルの他の項目も残してください。

```json
{
  "statuses": {
    "1": 1,
    "10001": 20001,
    "10002": null
  },
  "users": {
    "12345": 67890,
    "12346": -1
  }
}
```

左側が元のID、右側が先のIDです。右側は文字列ではなく数値で指定します。スペースが変わると同じ名称でもIDが異なるため、元の数値をそのままコピーしないでください。

`null` は未解決です。実際に課題で使用している値が未解決なら `check` で止まります。使っていない設定の `null` はそのままで構いません。

`users` のみ、`-1` を明示すると担当者を未設定にします。別の既存ユーザーIDに割り当てることもできます。過去の投稿者としてなりすます機能ではありません。

カスタム属性のリスト選択肢は `customFieldItems` で「元の属性ID → 元の選択肢ID → 先の選択肢ID」を対応付けます。

状態の対応付け例:

```text
元「レビュー中」ID 10001 → 先「レビュー中」ID 20001
```

同名が一意なら自動設定します。異なる名前を同じ状態とみなしたい場合は、人が対応先を指定してください。ツールは状態を追加・改名しません。

## 6. 実行前チェック（書き込みなし）

```bash
python3 backlog_migrate.py check
```

元の更新有無、各種ID対応、必須カスタム属性、親子課題設定、整形ルール、保存ファイルのSHA-256、先の既存課題などを確認します。レポートは `work/check_report.json` です。

`CHECK OK` になってから移行へ進みます。移行先設定に項目を追加した場合、`check` は最新の一覧を `destination_catalog.json` に再取得します。ただし `mapping.json` を勝手に書き換えないので、対応するIDは手動で反映してください。

`check` は読み取りで可能なチェックです。全書き込み権限・全プラン制限・あらゆるフィールド上限を保証するものではありません。

## 7. まず3件だけ移行

```bash
python3 backlog_migrate.py migrate --apply --limit 3
python3 backlog_migrate.py verify --deep --limit 3
```

**ここから先の `migrate --apply` が移行先に書き込みます。** `--apply` を忘れた場合、登録はせず停止します。

`--limit 3` は、スナップショットの先頭3課題に加え、必要な親課題も対象にします。したがって3件を超えることがあります。

移行先の画面で、本文・状態・担当者・親子関係・コメント・添付を確認してください。コメントの投稿者欄が移行実行ユーザーになるのは想定どおりです。元の投稿者はコメント本文にあります。

旧URLの参照や画像の埋め込みは自動修正しないため、画像の表示とリンク先も確認してください。

## 8. 同じ移行先へ全件を続ける

少数件の結果に問題がなければ、**設定・対応表・workを変更せず**そのまま全件を実行します。

```bash
python3 backlog_migrate.py migrate --apply
python3 backlog_migrate.py verify --deep
```

先ほどの3件分は処理記録を参照してスキップし、残りを進めます。

完全に別のテスト先から本番先へ切り替える場合は、コピーした別の設定ファイルと**新しい `work_dir`**を使い、`prepare` から実行します。テスト先の `state.json` を本番先に流用しないでください。

## 9. 中断・エラー後の再開

ネットワーク切断・Ctrl+Cなどで止まったら、**`work/` 全体を消さずに**同じ設定のまま再実行します。

```bash
python3 backlog_migrate.py migrate --apply
```

`state.json` に操作前・操作後の状態を保存します。成功レスポンスを受け取れなかった課題・コメント・添付は、移行先に記録した `BLMIG` 識別マーカーから登録済みかを確認します。

タイムアウトやサーバーエラーでは、登録済みの可能性があるためPOSTを無条件に再送しません。マーカーが見つからない場合は「結果未確定」として停止します。

### `結果未確定の操作` と出た場合

移行先の画面・ログを確認し、処理中のリクエストがなく、対象が本当に未登録であることを確認してください。**未登録を確認できた場合だけ**次を使えます。

```bash
python3 backlog_migrate.py migrate --apply --retry-pending
```

登録済みデータの識別マーカーを手で削除した場合などにこのフラグを使うと、重複する可能性があります。これは「とりあえず付ける」オプションではありません。APIとローカル状態の間に分散トランザクションはなく、どのような障害でも完全な一度限りの実行を保証するものではありません。

`state.json`、`snapshot.json`、添付ファイルを手動編集しないでください。最初の書き込み後に設定・対応表が変化すると停止します。マッピング変更が必要になった場合も、処理記録を消して同じ先にやり直さないでください。

## 10. 照合結果

```text
work/
  state.json                    途中再開用。削除厳禁
  issue_mapping.csv             旧課題キーと新課題キーの対応
  check_report.json             実行前チェック
  verification_report.json      照合結果
```

`verify` は移行先を読み取って、登録された課題の主要項目・親子関係・カスタム属性・コメント本文・添付の名前とサイズを照合します。`--deep` はファイルを再ダウンロードしてSHA-256も照合します。元の課題IDと更新日時が準備時から変わっていないことも確認します。

**照合対象外**: 画面の見た目、埋め込み画像・リンクの到達性、関連課題、共有ファイル、対象外のWiki・ドキュメント、各種通知・外部連携、完全な監査履歴。これらは別途確認が必要です。

元の更新日時比較だけで、全種類の同時更新を完全に検知できるとは限りません。移行中の書き込み停止は必須です。

`verify --deep --limit 3` は試行分だけの照合です。全件の照合には必ず `--limit` を外してください。先に全件 `verify` を実行すると、まだコピーしていない課題は未移行としてレポートされます。

## 11. オプションと安全装置

| オプション | 既定値 | 意味 |
|---|---|---|
| `request_interval_seconds` | 1.05 | 各APIクライアントでリクエスト間に待つ秒数。最低1秒 |
| `timeout_seconds` | 90 | 通信タイムアウト |
| `max_file_bytes` | 104857600 | このツールの1ファイル上限100MiB。Backlog側の契約・API上限とは別 |
| `copy_comments` | true | コメントを取得・コピー |
| `copy_attachments` | true | 添付ファイルを取得・コピー |
| `include_change_logs` | true | コメントの旧変更履歴を参照用テキストとして残す |
| `neutralize_mentions` | true | コピー本文中のメンション記法を文字に変換し、残りの `@` の後にもゼロ幅文字を挿入 |
| `allow_nonempty_destination` | false | 管理外の課題がある移行先への追加を許すか。既存課題との照合・統合・上書きはしない |

これらは `prepare` 前に決めます。準備後はオプションの変更を拒否します。

`neutralize_mentions=true` では、誤ったユーザー・全員への通知を避けるため、本文のメールアドレスなども厳密な同一文字列ではなくなります。元の文字列はローカルスナップショットに保存されます。メンション変換は通知の全面停止を意味しません。担当者への通知や外部連携が起きる可能性があります。

APIレート制限のヘッダーを監視し、HTTP 429は待機して再試行します。GETの一部一時エラーも再試行します。POST・PATCHの通信断／5xxを無条件で繰り返さない設計です。

APIキーは `Backlog-API-Key` ヘッダーで送信し、URLに入れません。TLS検証を有効にし、リダイレクトには追従しません。正規のダウンロードでもリダイレクトが必要な環境では停止するため、その場合は応答を調査してください。キーの第三者ホストへの転送を避けるための制約です。

アップロード時はファイルをメモリに読み込みます。上限を引き上げると必要なメモリも増えます。ファイル名に改行・ダブルクォート・バックスラッシュがある場合は、無断で改名せず安全のため準備段階で止まります。

クライアント側にも許可APIのチェックがあります。移行元はGETのみ許可。移行先の書き込みは課題追加・課題更新・コメント追加・一時添付アップロードに限定しています。状態追加・ユーザー追加・プロジェクト変更・削除APIは許可しません。

## 12. よくある停止原因

| メッセージ・症状 | 確認すること |
|---|---|
| APIキーが未設定 | 同じターミナルで `source ./api_keys.sh` を実行 |
| 401 / 403 | キー・ユーザー権限・プロジェクト参加・アクセス制限を確認 |
| `statuses ... 未設定または無効` | 移行先に既存の該当状態があるか。`mapping.json` の先IDを修正 |
| `users ... 未設定または無効` | ユーザーを移行先プロジェクトに参加させ、先IDを指定。未設定にする場合のみ `-1` |
| `管理外の課題` | 公式ツールの途中データ等が残っている。空のテスト先を推奨 |
| 必須カスタム属性の値がない | 型・適用する種別・値・定義が移行先と一致しているか確認 |
| 「その他入力」 | この版は未対応。元を変更せず、レポートの該当属性を確認 |
| `移行元...変化` | 準備後に元が変更された。自動差分同期はしない。既に書き込み済みならworkを保持し、単純な再prepareをしない |
| `JSONでない応答` / 3xx | URL・認証・ネットワークを確認。キーやTLS検証を無効にして強引に進めない |
| 容量・添付数・本文長などの400 | Backlog側の制約。既にコピー済みのものがあるため、workを消さず原因を確認 |

## 13. テスト

外部APIを呼ばずに以下を実行できます。

```bash
python3 -m unittest discover -s tests -v
```

同梱の `TEST_RESULTS.txt` は作成時の結果です。33テストが成功しました。主に、12状態を設定した状態でのコピー、401件の一覧ページング、251コメントのページング、親子関係・各種項目・添付、少数件→全件の再開、応答消失後の復旧、添付登録後のGET失敗、二重登録防止の停止動作、SHA-256不一致、ID未対応、既存先の保護、APIキー秘匿、HTTP 429、multipart送信等を確認しています。

**この結果は実際のBacklogサーバーでの疎通・動作確認ではありません。** APIの実応答・権限・データ形式は少数件の試行で必ず確認してください。

## 14. 作業後

照合レポート・対応表・元データ・処理記録は、社内の情報管理ルールに沿って保管します。不要になったキーは失効させてください。

```bash
unset BACKLOG_SRC_API_KEY BACKLOG_DST_API_KEY
```

環境変数を消してもBacklog側のキーを失効したことにはなりません。必要に応じて個人設定で削除してください。
